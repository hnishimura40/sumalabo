# Editorial Selection

## 採用する主軸

スペックやベンチマークではなく、CodexとClaude Codeの両方を運用した当事者が「作業の入口」で使い分ける。特に、内蔵ブラウザと既存Chrome、画像のUI搬出とファイル直保存の差を一般読者の判断材料へ翻訳する。

## 採用する論点

1. Codexは「コードを書くAI」より、ファイル・ブラウザ・画像・検証をまたいで完了条件まで進む働くAIと説明する。
2. 内蔵ブラウザは専用プロファイル、Chrome拡張は普段のChromeという差を、ログイン・準備・安定性の3軸で整理する。
3. Claude CodeとClaude for Chromeを混同しない。Claude Codeはターミナル/デスクトップ側、ブラウザ操作はClaude for Chromeと明示する。
4. 本サイトの画像運用変更は1段落に抑え、誇張せず「生成以前の格闘が消えた」と説明する。
5. 結論は4象限（会話と執筆 / コード / ブラウザ / 画像量産）。どちらが上かではなく、何をさせたいかで選ぶ。

## 採用しない論点

- SWE-benchなどのベンチマーク優劣
- モデル知能のランキング
- 一時的な利用上限を恒久仕様のように扱うこと
- Claude CodeのChrome拡張という不正確な呼び方
- 1サイトの運用実例を全ユーザーへ一般化すること

## 読者が持ち帰る判断

- ログイン済みサイトを触らせたい → 普段のChromeを使える拡張が便利
- 作ったWebをlocalhostで確認し、環境を分離したい → 内蔵ブラウザが便利
- コード中心 → どちらも候補。既存の開発習慣と指示資産で決める
- 画像を繰り返しファイル化したい → UI操作の段数より、保存まで自動化できる経路を優先
