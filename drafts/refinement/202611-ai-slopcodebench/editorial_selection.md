# Editorial Selection：SlopCodeBench

判定: 限定採用

## 採否の理由と記事の核

**「AIにプログラムの機能追加を任せ続けたとき、何を確かめる評価なのか」を解説する記事として採用する。**

調査報告には、評価の設計、論文の結果、追加検証の条件を説明できる一次資料が整理されている。一方、「AI自身の能力が長時間の使用で低下する」「11月に新しい評価が登場した」という切り口は裏付けられていない。

記事の核は、**新しい機能が動くこと、以前の動作も保つこと、コードの整理状態を保つことの違い**とする。AIの全面的な優劣や、特定サービスへの乗り換えを結論にしない。

カテゴリは「ニュースをかみくだく」。当サイトによる実行検証や実体験はなく、hands-onには分類しない。

推奨タイトル：

**AIに機能追加を任せ続けると？「SlopCodeBench」が測る動作とコードの変化**

## なぜ今取り上げるか

11月12日のGIGAZINE報道が、読者へ紹介する契機になる。ただし、研究そのものの初出と報道日を分ける。

| 時点 | 調査報告で確認された出来事 | 記事での位置づけ |
|---|---|---|
| 2026年3月25日 | 論文初版の提出 | 研究の経緯 |
| 2026年5月7日 | 論文改訂版の提出 | 主な評価条件と研究結果 |
| 2026年10月15日 | 別の実施者による追加検証 | 条件付きの補足資料 |

編集上の価値は、単発の課題の成功だけでは読み取れない、変更を重ねる開発の評価方法を説明できる点にある。複数媒体での広がりは確認されていないため、「世界で話題」「急速に注目を集める」とは書かない。

## 答える読者の疑問とAIの視点

| 読者の疑問 | 解説する内容 |
|---|---|
| どんな試験なのか | 自分で作ったプログラムを引き継ぎ、段階的に追加要求へ対応する仕組み |
| 新機能が動けば成功ではないのか | 今回の要求への合格と、以前から引き継いだ要求を含む合格の違い |
| コードが悪くなるとは、バグが増えることか | 動作の検査と、処理の複雑さ・重複を調べる指標の違い |
| 数字が低いAIは、仕事でも使えないのか | 評価条件が限られ、実務の失敗率へ置き換えられない理由 |
| 自分の使い方にも関係するのか | 継続的なプログラム開発との関係と、文章相談などへの一般化の限界 |

AIの視点は、「作れるか」に加えて「変更を重ねられるか」という評価の違いを理解するために使う。AIが疲れる、飽きる、考えすぎるといった擬人化で原因を説明しない。

## 論点の取捨選択

| 論点 | 扱い | 根拠・条件 |
|---|---|---|
| 過去のコードを引き継いで追加要求へ対応する設計 | 採用 | 調査報告F1。記事の中心に置く |
| 動作の合否とコードの整理状態を別々に測ること | 採用 | F3・F4。両者の混同を防ぐ |
| StrictとIsoの違い | 採用 | F4。何に合格した数値かを説明する |
| 改訂版の36問題・196段階という規模 | 採用 | F2。196段階を196個の独立した問題と言い換えない |
| コード構造の指標が増加したという研究結果 | 限定採用 | F3。対象とした評価の範囲に限定し、品質指標をバグ率にしない |
| 初版と改訂版の最高合格率の差 | 限定採用 | F2。対象が違うため時系列の性能比較には使わない。必要時の補足に留める |
| 10月の追加検証 | 限定採用 | F6・F7。論文とは別の実験で、各条件1回であることを添える |
| 最新順位によるおすすめAI選び | 不採用 | 指標ごとに首位が異なり、実行ツールや設定も揃っていない |
| 推論量を減らせば改善するという助言 | 不採用 | 因果関係が未確定 |
| コードの94%がバグという説明 | 不採用 | 検出規則に該当した行の割合とバグ率を混同している |
| 人間より保守能力が低いという結論 | 不採用 | 同一課題・同一条件の対照実験ではない |
| 日本語での性能、日本からの実行成功 | 不採用 | 調査報告では未確認 |
| 導入手順、料金比較、設定の推奨 | 不採用 | 今回の解説の核を外れ、利用条件の追加確認も必要 |

数値を載せる場合は、論文の版、対象、指標の意味、実行条件を近くに記す。細かなモデル順位や費用倍率は主見出しに使わない。

## 読者翻訳設計

この節は内部設計用であり、公開本文へコピーしない。

### 主題の一言説明

AIが作ったプログラムに機能を追加し続けたとき、必要な動作とコードの整理状態が保たれるかを調べる試験の話。

### 関係がある人

- AIにアプリや業務用プログラムを作らせ、後から機能追加や修正を繰り返す人。
- AIの開発能力を示す成績表を見て、何が測られているか理解したい人。

### あまり関係がない人

- AIを文章の相談、要約、単発の画像生成などに使っている人。
- プログラムの継続開発を任せていない人。この研究だけを理由に、今の利用方法を変える必要があるとは言えない。

### 公開本文で使う専門用語と説明

以下を本文の使用予定表記とする。各語は初出の同じ文か直後で説明する。本文で新たに専門語を追加する場合は、この一覧も更新する。

- AI → 文章などの入力を受けて、回答やプログラムを作る人工知能。
- AIコーディングエージェント → 指示に沿ってプログラムを書き、修正作業も進めるAIの仕組み。
- SlopCodeBench → AIにプログラムの変更を繰り返させ、動作とコードの状態を調べる試験の仕組み。
- ベンチマーク → 決めた課題と条件で、できることを測って比べる試験。
- コード → コンピューターに行わせる処理を書いたもの。
- チェックポイント → 新しい要求が加わり、出来上がりを調べる開発の一区切り。
- テスト → プログラムが求められた動きをするか確かめる検査。
- Strict → 今の段階の検査と、以前の段階から引き継いだ検査の両方に合格する厳しい判定。
- Iso → 以前の段階からの検査を除き、今の段階の検査で合格するかを見る判定。
- Erosion → 複雑な処理がプログラムの一部にどれほど集中しているかを表す指標。
- Verbosity → 決めた検出規則で拾われる記述や、似た構造が繰り返される記述の行の割合を表す指標。
- Python → この論文の評価で使われた、プログラムを書くための言語。

実行環境の製品名や設定名は、公開本文では必要な条件を日本語で説明する。指標名の別名・略称は増やさない。

### 事実から言えること

- 自分のコードへ変更を重ねる過程を評価する仕組みである。
- 新しい要求への対応と、以前から引き継いだ動作の維持を区別して成績を読める。
- 論文で調べた条件では、変更の反復に伴いコード構造の指標が増加する傾向が報告されている。
- 動作に関する成績と、コードの整理状態に関する数値は、異なる側面を測っている。

### 事実から言えないこと

- AI自身の能力が時間とともに低下したこと。
- 長く使えば、すべてのAI・すべての用途で必ず失敗すること。
- コード構造の変化が、動作不良の原因だと立証されたこと。
- 品質指標の割合が、そのままバグの割合や保守費用を表すこと。
- 評価の合格率を、実務での成功率・失敗率へ置き換えられること。
- 日本語で依頼する場合にも、同じ結果になること。

## 本文へ引き継ぐ説明方針

説明順は「これは何か → 自分に関係するか → 今回紹介する内容と時系列 → 何を理解する助けになるか → 注意点 → 詳しい条件」とする。

日常の例を使うなら、**「たとえると、アプリへ検索機能を追加した後も、それまでの保存機能が動くか確かめるようなもの」**と示す。実際の出題内容として扱わない。

ひまりの疑問は「追加した機能が動けば、それで合格じゃないの？」とする。らぼまるは「以前から必要だった動作も確かめる判定がある」と整理し、StrictとIsoの比較へつなぐ。

読者への実用的な示唆は、記事の後半に短く置く。

> AIへ変更を頼むときは、追加した機能と、それまで必要だった動作を分けて確認するという見方が役立つ。

これは編集上の示唆であり、その確認方法で問題を解消できると本研究が実証したわけではない。

## 出典の使い分けと留保

本選定は、2026年11月13日付の調査報告を根拠とする。本工程では外部原資料の再取得、原データの独立再集計、当サイトでの実行検証は行っていない。

- 評価条件と研究結果は、[論文改訂版](https://arxiv.org/html/2603.24755v2)を中心に説明する。
- 評価の目的は、[開発元の設計方針](https://www.scbench.ai/design-philosophy)に帰属させる。
- 指標の説明は、[公式ランキング](https://www.scbench.ai/leaderboard)の定義を使う。順位を載せる場合は更新表示日と調査報告の確認日を添える。
- [10月の追加検証](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/benchmarking-new-models-on-slop-code-bench.md)は、別の実施者による実験として区別する。
- [GIGAZINEの報道](https://gigazine.net/news/20261112-slopcodebench/)は紹介の契機として扱う。調査報告には直接取得の失敗が記されているため、報道本文の直接引用には使わない。

日本の読者との関係は、AIによる継続開発の評価を理解する点に置く。日本での提供開始や日本語性能のニュースへ置き換えない。

## 選定段階の見直し

- **1回目：事実と表現の点検。** 新規発表、AI自身の能力低下、品質指標とバグ率の混同につながる切り口を除外した。
- **2回目：読者理解と範囲の点検。** 評価の意味を主軸にし、細かな順位、設定推奨、導入解説を外した。関係が薄い読者と専門語の説明を明記した。
